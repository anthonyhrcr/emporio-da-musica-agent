# Empório da Música — customer-service agent

A prototype text-message agent for **Empório da Música**, a (fictional) musical-instrument store in
Campo Grande/MS. Built for the Artefact AI Engineer technical case.

The agent, **Lia**, answers customers in Brazilian Portuguese, in the tone the store's manual asks for,
and decides on every message whether it needs **store data** (catalogue, prices, stock, promotions,
orders) or **store policies** (hours, payment, returns, shipping, warranty), and when a question is
outside the store's scope or needs a human.

- **[examples/](examples/)**: five real conversations, generated by running the agent, unedited
- **[tests/](tests/)**: 52 tests for the rules that must be exactly right and for the guardrails, with no model needed
- **`python -m emporio.data`**: the data-quality report behind section 5

---

## 1. Running it

Requirements: Python 3.11+ and either [Ollama](https://ollama.com) (the default: local, free, no key)
or any OpenAI-compatible API.

```bash
git clone https://github.com/anthonyhrcr/emporio-da-musica-agent.git
cd emporio-da-musica-agent
python -m venv .venv && source .venv/bin/activate
pip install -e . pytest

ollama pull qwen3:8b               # ~5 GB, once
python -m emporio.cli --debug      # chat; --debug prints every tool call
```

Inside the chat: `/novo` starts a new conversation, `/sair` quits. Each conversation is saved as
Markdown in `runtime/conversations/`.

| Command | What it does |
|---|---|
| `python -m pytest` | 52 tests (pricing, hours, policies, verification, returns, guardrails), runs in < 1 s |
| `python -m emporio.data` | Data-quality report over the CSVs |
| `python scripts/run_examples.py` | Regenerates the five example conversations |
| `STORE_NOW=2026-03-25T10:30 python -m emporio.cli` | Freezes the store clock (see Assumptions) |

**Another provider:** copy `.env.example` to `.env` and change three lines. For example, OpenAI:
`LLM_BASE_URL=https://api.openai.com/v1`, `LLM_MODEL=gpt-4o-mini`, `LLM_API_KEY=sk-...`, and leave
`LLM_REASONING_EFFORT=` empty (that model doesn't accept the parameter). Gemini and Groq work the same way
through their OpenAI-compatible endpoints.

*Troubleshooting:* if `import emporio` fails after `pip install -e .`, run with `PYTHONPATH=src`. On
recent macOS, files inside `.venv` can get the "hidden" flag, and Python 3.12+ skips hidden `.pth` files.

## 2. How it works

```
customer message
      │
      ▼
┌───────────────┐   system prompt: persona · routing rules · scope · live store clock
│  agent loop   │◀──────────────────────────────────────────────────────────────┐
│  agent.py     │                                                                │
└──────┬────────┘   function calling, OpenAI-compatible API ──▶ qwen3:8b on Ollama
       │ tool calls / JSON results                                (or any provider)
       ▼
┌──────────────────────────────── tools.py ─────────────────────────────────────┐
│ DATA                               │ POLICIES             │ HANDOFF             │
│ search_products                    │ get_policy(section)  │ escalate_to_human   │
│ get_product_details                │                      │   → protocol number │
│ list_active_promotions             │                      │                     │
│ lookup_orders         (verified)   │                      │                     │
│ check_return_options  (verified)   │                      │                     │
└────────────┬───────────────────────┴───────────┬──────────┴─────────────────────┘
             ▼                                   ▼
 data.py · pricing.py · clock.py           policies.py
 CSVs → typed records; prices, PIX,        PDF → 10 numbered sections,
 installments and dates computed in code   plus notes on contradictions
```

| Module | Responsibility |
|---|---|
| `data.py` | Loads the CSVs into typed records (money as `Decimal`) and builds the data-quality report |
| `pricing.py` | PIX discount, promotion rules, installment tiers. Every price the agent quotes comes from here |
| `clock.py` | Opening hours against Campo Grande local time (UTC−4), including fixed national holidays |
| `policies.py` | Splits the policy PDF into its numbered sections and attaches curator notes where the manual contradicts itself |
| `tools.py` | The seven tools the model can call, their JSON schemas, and identity verification for orders |
| `prompts.py` | Persona, routing rules (data vs. policy vs. human), scope and grounding rules |
| `agent.py` | The tool-calling loop, conversation history and the two guardrails |
| `cli.py`, `transcript.py` | Terminal chat; conversations rendered as Markdown with the tool calls visible |

## 3. Technical decisions

### Agent approach: function calling with typed tools

The questions customers ask are few and recurring (the brief lists them, and so does the manual's
standard flow in 7.2). Each one became a tool with typed arguments. I considered two alternatives.

- **SQL agent (text-to-SQL).** Rejected because the tables hold customers' personal data. A model
  writing free SQL can read any row, so "only show an order to its owner" would be an instruction in a
  prompt rather than a guarantee. With typed tools, `lookup_orders` *cannot* return an order unless the
  contact matches, whatever the model writes.
- **Letting the model do the arithmetic.** The payment rules are arithmetic: 5% PIX discount, no stacking
  with promotions, three installment tiers with different minimums. An 8B model computing a price is the
  most likely way to quote a wrong one, and the manual itself says wrong prices "podem configurar
  propaganda enganosa" (7.1). So `pricing.py` computes every value, and the prompt tells the model to
  copy numbers, not calculate them.

**Trade-off:** questions that don't fit a tool (say, "which brand sells the most?") can't be answered.
For customer service that is acceptable: the agent says it doesn't have that information and offers a
human.

### Retrieval over policies: whole-section lookup, not embeddings

The manual is 8 pages (~10k characters) and already divided into 10 numbered sections. `get_policy` takes
one of 10 section keys, as an enum in the schema, and returns the whole section.

- **Why not vector RAG?** Chunk boundaries are where retrieval over policies fails. A return rule
  retrieved without its exclusions (4.1 without 4.4) produces a confident wrong answer. Whole sections
  keep every rule next to its exceptions.
- **Why not paste the whole manual into the system prompt?** It would work, but every turn would pay for
  ~3k extra tokens on a local model, and it would hide the decision the brief asks to see: *when* to
  consult policies. With a tool, that choice shows up in the logs (`get_policy("trocas_e_devolucoes")`).
- **Parsing detail:** pypdf's default extraction returned one word per line, so it uses layout mode. The
  numbered steps inside 7.2 ("1. Saudação", "2. Entendimento"…) look like section headings, so the
  splitter only accepts the *next expected* section number. There is a test for it.

**What would change at scale:** with hundreds of pages I'd add embeddings over subsections and keep the
section key as a metadata filter.

### Model and provider: qwen3:8b on Ollama, behind an OpenAI-compatible client

- **Local by default.** Evaluators can run it without an API key or cost. Customers' names, phones and
  orders never leave the machine, which fits the manual's LGPD section (9). Results are reproducible.
- **qwen3:8b.** Good Portuguese, native tool calling, and it runs on a 16 GB laptop.
- **OpenAI-compatible client.** The same code runs against OpenAI, Gemini, Groq or vLLM by editing
  `.env`. Nothing in the agent is Ollama-specific.
- **Reasoning off, measured.** qwen3 runs a hidden reasoning pass by default. The documented `/no_think`
  prompt switch was ignored through Ollama's OpenAI endpoint: a one-line answer took 13.4 s and 259
  tokens. Passing `reasoning_effort="none"` took 2.0 s and 33 tokens. In the agent, turns went from
  28–42 s to 6–17 s.
- **Trade-offs:** latency (fine for a prototype, too slow for production chat) and occasional stylistic
  slips from a small model (see section 6). A hosted model would be faster and sharper without any
  architecture change.

### Interface and conversation history

- **Interface:** a terminal chat. The brief says the focus is the agent, and `--debug` makes every tool
  call visible.
- **History:** the full conversation, including tool calls and their results, is kept for the session.
  That lets follow-ups like "e no PIX?" reuse the product that was just looked up. Each conversation is
  saved as a Markdown transcript when it ends.
- **No memory across sessions, on purpose.** In a real WhatsApp deployment the session would be keyed by
  the phone number the channel provides, and a CLI has no identity to key it on. It also avoids keeping
  personal data longer than needed (LGPD data minimisation).

### Data handling

- **Files:** renamed to remove spaces and accents, so paths are portable. Contents are untouched.
- **Loading:** typed records, with money as `Decimal` (never floats).
- **Nothing fixed silently.** Inconsistencies are reported (section 5), and the agent shows what the
  system recorded. For example, an order total that doesn't match its items is shown as charged, not
  "corrected".
- **Availability:** derived from both `status` and `stock_quantity`. A product is available only if it
  is `active` with stock above 0. `discontinued`, `coming_soon` and zero-stock products each get their own
  message and a list of alternatives (7.3).

### Prompt strategy

- **Persona** taken from manual 7.1: informal but professional, "como um amigo que entende de música",
  messages sized for a phone.
- **Explicit routing rules:** prices, stock and promotions go to data tools; rules go to `get_policy`;
  complaints, defects, cancellations and shipping outside the metro area go to `escalate_to_human`.
- **Grounding rules:**
  - use only what tools returned, and copy numbers verbatim
  - show original price, percentage and promotional price (the transparency rule in 6.2)
  - say plainly when a promotion has ended (7.3)
  - don't invent partner stores (the manual mentions them but lists none)
- **Live context:** the store's clock (open or closed, and when it reopens) is injected, and the prompt
  is rebuilt on every call so it is never stale.
- **Principle: the prompt asks, the code guarantees.** Anything that must hold (prices, deadlines, who
  may see an order) is enforced in the tools, not just requested in the prompt.
- **No category list in the prompt.** It was there in the first version, and the model used it to answer
  "Vocês têm saxofone?" with "Tem sim!". The store has the category but no products in it. The tool
  schema already enumerates categories, so the list was removed.

### Two guardrails, enforced in code

The example runs showed that prompt rules alone are not enough for an 8B model (section 6). It
invented a store address, confirmed saxophones the store doesn't have, and mis-copied a price. So
`agent.py` checks every reply before the customer sees it.

1. **Looked up?** The customer's message is matched against seven store topics: hours, address and
   contact, payment, returns and warranty, shipping, prices and stock, and orders. Every instrument
   category and brand named also counts as a topic. Each topic must have been consulted with a fitting
   tool somewhere in *this conversation*. "E no PIX?" right after a product lookup is covered. "Qual o
   endereço?" in the middle of a product chat is not, and neither is "e saxofone?" after a guitar
   search.
2. **Traceable?** Every R$ value, full date, phone number and street address in the reply must appear
   in a tool result, the system prompt or the customer's own messages. The model's earlier replies don't
   count as a source, because that is exactly how a mis-copied price spreads.
3. **Nothing the store doesn't have.** A reply may not name an instrument type the catalogue has zero
   products of, unless the customer used that word. "Não temos saxofones" is fine, because the customer
   asked about saxophones. "Posso te ajudar com trompetes" is not, because the store has no brass at
   all.

**What happens on a problem:**
- **The code looks it up itself.** If a lookup was skipped and the right call is unambiguous, the code
  makes the call and the model answers again with the data in context. "Abre sábado?" maps to the hours
  section, and "tem saxofone?" maps to a catalogue search. This doesn't depend on a small model obeying
  an instruction. Ollama also ignores `tool_choice="required"` (tested), so the call can't be forced
  any other way.
- **One retry.** When the code can't make the lookup itself (an order needs the customer's contact; a
  price needs to know which product) or a value has no source, the reply is discarded. The model gets one
  specific instruction naming what's missing.
- **Then an honest fallback.** If the problem persists, the customer gets *"Não consegui confirmar essa
  informação no sistema agora…"* and an offer to involve the team.

Automatic lookups appear in the transcripts as ordinary tool calls, marked *"feita automaticamente pelo
guardrail"*.

**Exemptions:**
- asking the customer for their phone or e-mail, which is the correct first step before an order lookup
- small talk and accessory questions, which name no store topic

**How it's tested:** the topic match is plain keywords and brand names, and the model plays no part in
it. Every failure from runs 1–3 is replayed by a scripted fake model in `tests/test_agent_guardrail.py`.

**What it can't catch:** a wrong *qualitative* claim in general. Check 3 exists because one such
claim kept coming back: runs 2, 3 and 4 each offered wind instruments right after the search said there
were none (clarinetes e oboés, trompetes ou tubas, trompetes ou trombones). Rewording the tool output
didn't stop it, so it became a deterministic check. A free-text claim like "this guitar is great for
beginners" can't be verified by keywords (section 8).

### Privacy (LGPD)

- **Verification first:** order data requires the phone (any format) or e-mail on file.
- **No enumeration:** the answer is identical whether an order number doesn't exist or belongs to
  someone else.
- **Ambiguous contacts:** an e-mail shared by two registrations is treated as ambiguous, and the agent
  asks for the phone instead.
- **Minimal output:** tools never return other customers' data, and escalation tickets are written
  locally only.

## 4. Assumptions

Where the brief or the data was ambiguous I chose a reading and kept going, as the brief asks.

| Topic | Assumption |
|---|---|
| "Today" | The data is a snapshot (latest order: 22/03/2026). The examples run with the store clock frozen at **25/03/2026 10:30**, so 7- and 30-day rules are evaluated on the data's own timeline. Without `STORE_NOW`, the agent uses the real time in Campo Grande. |
| Date of receipt | The system has no "received on" field. `estimated_delivery` is used as the receipt date for the 7-day regret window (4.1) and the 90-day legal warranty (8.1), and the agent says it is an estimate. |
| Exchange by preference (4.3) | "Até 7 dias" is counted from receipt, like 4.1. |
| Installments | Section 3.1 overrides the summary table. "Até 3x sem valor mínimo (exceto abaixo de R$ 50,00)" is read as *each installment ≥ R$ 50*. |
| Promotions | Only `is_active = 1` applies. If several were active for one product (none today), the best one for the customer applies, since they don't stack. |
| Budget filters | "Até R$ 1.000" compares the final price after any promotion, before the PIX discount. |
| Holidays | Fixed-date national holidays only (see Limitations). |
| Cancelling an unshipped order | The manual doesn't cover it, so the agent escalates to a human and never promises it. |
| Shipping outside the metro area | Priced "by CEP" in the manual, with no table, so the agent escalates instead of quoting. |
| Order status `pending` | Not defined anywhere, so it is shown as "pendente" without guessing what it means. |
| Manual contradictions | WhatsApp **(67) 3341-4444** and e-mail **without accent**: see the next section. |

## 7. Tests

52 tests that run without a model. `tests/test_rules.py` covers the deterministic rules:

- **Pricing:** PIX discount, no stacking with promotions, installment tiers at their boundaries, and
  combined payment only above R$ 2.000.
- **Opening hours:** 18:00 and Saturday 13:00 closing times, Sunday, and Finados, plus "reopens Monday
  at 09:00".
- **Policy splitting:** ten sections, with the numbered steps of 7.2 kept inside section 7.
- **Verification:**
  - a wrong contact gets nothing
  - another customer's order is never shown
  - the shared e-mail asks for the phone
  - three phone formats all match
- **Returns:** the 7-day window closed after 36 days, an **expired deadline never offered as open**,
  a defect after 30 days routed to the legal warranty, unshipped orders escalated, and a protocol for
  complaints.

`tests/test_agent_guardrail.py` drives the real agent loop with a scripted fake model and replays every
failure from runs 1 and 2:
- the saxophone claim, now answered by an automatic search
- the invented address, stopped even when the model insists after the lookup
- the Saturday hours answered without the hours lookup, now looked up automatically
- the PIX follow-up that must be *accepted*
- the mis-copied R$ 849,90, an invented phone number and invented street addresses
- trumpets and trombones offered after a search that found no wind instruments, while "não temos
  saxofones" (echoing the customer's own word) stays allowed
- a model that insists on a wrong value, which gets the honest fallback

It also checks that asking for a contact and small talk are left alone.

The model's behaviour is checked through the example conversations, not unit tests. Section 8 describes
how I'd test it properly.

## 8. Known limitations and what I'd do with more time

1. **An evaluation set for the model's behaviour.** About 50 scripted questions with expected tool calls
   and assertions on the reply (for example, every R$ value in the answer must appear in a tool result
   from that turn), run in CI. That's how I'd compare models and prompt changes instead of reading
   transcripts by eye.
2. **Qualitative claims.** The guardrails check that every topic was looked up, that every number,
   date, phone and address traces back to a source, and that no instrument the store lacks is offered.
   They can't verify free-text claims ("ótimo para iniciantes"), offers of features that don't exist
   ("te aviso quando chegar"), or small slips (in run 4 it called the customer by the agent's own name).
   Options, cheapest first:
   - a check that actions claimed in a reply ("vou encaminhar", a protocol number) match a tool call
     made in that turn (run 5, example 03)
   - a second, small model call that checks the reply against the tool results
   - structured replies, where the model fills fields and code writes the sentence, for critical
     answers
3. **Latency.** Typically 6–17 s per turn locally, plus one more model call when a guardrail retry
   happens. Next steps would be a hosted model or a smaller quantised one,
   streaming replies, and caching the static part of the prompt.
4. **A small model's slips.** It occasionally uses an English word or more emoji than the prompt allows,
   and on a follow-up it may answer from the conversation history instead of calling the tool again.
   That's correct when the data came from the same conversation minutes earlier, but it would be stale
   in a long session.
5. **A real channel.** A WhatsApp Business webhook (FastAPI) with one session per phone number. The
   channel's verified phone would replace asking the customer for it.
6. **Integrations still missing:**
   - shipping quotes by CEP (Correios and Jadlog APIs)
   - tickets sent to a real helpdesk instead of a local JSONL file
   - movable, state and municipal holidays
   - reading live data from the store's system instead of CSV exports

## 9. Use of AI coding assistants

I built this with **Claude Code** (Anthropic's terminal coding agent, model Claude Opus 5.5) as a pair
programmer, in one evening. The brief asks how it was used, so here is the actual split.

- **What I decided:**
  - run on a local model, so evaluators need no key and customer data stays on the machine
  - work in a public repo and commit as the work progressed
  - submit within the original deadline instead of assuming the extra day the Finados holiday might
    have given

- **How we worked: run it before trusting it.** Several decisions in this README came from running
  something rather than from reading code:
  - pypdf's default mode returned one word per line, so the splitter uses layout mode
  - qwen3 ignored the `/no_think` switch (measured 13.4 s vs 2.0 s), so the agent uses
    `reasoning_effort`
  - what looked like an identity-verification bug, a "made-up" phone number that matched a customer,
    turned out to be a real customer whose phone *looks* fake. It is reported in section 5 rather than
    "fixed".
  - each example run was read line by line rather than skimmed:
    - run 1 surfaced two hallucinations and a deadline bug in my own tool
    - run 2 showed that the first guardrail was both too loose (one lookup vouched for two topics) and
      too strict (it blocked correct follow-ups)
    - run 3 showed that a safe fallback can still be a useless answer, which led to the automatic
      lookups
    - run 4 showed one failure surviving three rounds of tool rewording, which became a deterministic
      check
    - all failing runs are kept in the history on purpose (section 6)
